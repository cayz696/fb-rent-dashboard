## 1. Мета

Зробити єдиний вебінтерфейс, де видно кожен акаунт на кожному етапі, кому він виданий, скільки відкрутив і що з ним відбувалось. Заявки клієнтів приходять з Telegram, розбираються автоматично і видаються після апруву адміна. Google Sheets та інші таблиці не використовуються.

Що система НЕ робить: не автоматизує дії всередині інтерфейсу Facebook (створення БМ, прив'язку номерів і карт, запуск реклами). Ці кроки виконує людина, а система фіксує факт і час виконання.

## 2. Архітектура

```
┌──────────────── VPS (24/7) ────────────────┐        ┌──── MacBook ────┐
│  Web UI (Next.js)                           │        │  AdsPower       │
│  API (FastAPI)  ── Postgres                 │◄──WS──►│  Bridge agent   │
│  Telegram bot (aiogram)                     │        │  (Python)       │
│  LLM agent (tools → API)                    │        │  → Local API    │
│  /api/clover/spend  ◄── Clover Spend Export │        │    :50325       │
└─────────────────────────────────────────────┘        └─────────────────┘
```

- **Сервер** — усе, що має працювати цілодобово: UI, API, база, бот, агент, прийом даних Clover.
- **Bridge** — легкий процес на машині з AdsPower. Сам підключається до сервера (WebSocket + токен, або через Tailscale), отримує команди з черги, викликає AdsPower Local API, повертає результат. Сервер ніколи не звертається до макбука напряму.
- Якщо bridge офлайн, команди лишаються в черзі зі статусом `pending`, UI показує стан «міст офлайн».

| stage | enum | див. розділ 5 |
| off_reason | enum null | `ban`, `reserve`, `paused`, `returned`, `written_off` |
| supplier_id | fk | |
| batch_id | fk | партія закупівлі |
| purchase_cost | numeric | собівартість |
| client_id | fk null | поточний клієнт |
| adspower_profile_id | text null | ID профілю в AdsPower |
| ad_account_id | text null | ID рекламного кабінету, ключ зшивки з Clover |

| card_last4 | char(4) null | тільки останні 4 цифри |
| timezone | text null | з Clover |
| spend_limit | numeric null | з Clover |
| check_until | timestamptz null | кінець перевірки 24 год |
| notes | text | лише для адмінів |
| created_at / updated_at | timestamptz | |

### account_events — журнал (тільки вставка, без редагування)
`id, account_id, type, from_stage, to_stage, payload jsonb, actor (user_id | 'clover' | 'bridge' | 'agent'), created_at`

### clients
`id, name, telegram_chat_id, telegram_usernames[], terms (напр. % від спенду), balance, status, notes`

### requests — заявки з Telegram
`id, client_id, raw_text, message_link, parsed jsonb, status (new|proposed|approved|rejected|done), proposed_account_ids[], approved_by, created_at`

### suppliers, batches
`suppliers: id, name, contact, notes` · `batches: id, supplier_id, qty, unit_cost, bought_at`

### spend_snapshots — дані Clover
`id, ad_account_id, account_id (nullable, якщо не зіставлено), date (в TZ системи), spend_today, spend_total, spend_limit, ads_active, ads_issues, status_raw, raw jsonb, received_at`

### bridge_commands
`id, command, args jsonb, status (pending|sent|ok|error), result jsonb, created_by, created_at, done_at`

### users
`id, name, role (admin|operator|viewer), totp_enabled, created_at`

**Заборонено зберігати:** повні номери карт, паролі від акаунтів, cookies, TOTP-секрети. У системі лише посилання на них (наприклад, «запис у менеджері паролів №…»).

## 5. Статус-машина акаунта

```
purchased → in_adspower → bm_created → phone_linked → warmup → card_linked
→ checking (24h) → ready → issued → (returned → ready | off)
будь-який етап → off (з обов'язковою off_reason)
off(reserve|paused) → ready
```

Правила:
- Перехід можливий лише по дозволених стрілках. Інакше API повертає 409.
- Кожен перехід пише запис у `account_events` з автором.
- `checking`: при вході ставиться `check_until = now() + 24h`. Фонова задача за 30 хв до кінця створює сигнал «перевірка завершується».
- `issued` вимагає `client_id` і пов'язану `request` або ручне підтвердження адміна.
- Перехід у `off` вимагає `off_reason` і коментар.

## 6. Інтеграції

### 6.1 Clover Tool (Spend Export)
- Ендпоінт `POST /api/clover/spend`, авторизація секретом у заголовку або в URL-токені (налаштовується в `.env`).
- **Формат payload поки невідомий.** Етап 1: ендпоінт зберігає сирий JSON у `spend_snapshots.raw` і логує. Етап 2: після отримання прикладу пишеться парсер (окремий модуль `clover_mapper.py`), який заповнює структуровані поля.
- Зіставлення з акаунтом: за `ad_account_id`. Незіставлені записи показуються в UI у розділі «Нерозпізнані кабінети» з кнопкою прив'язки.
- Усі дати зводяться до часового поясу системи (Europe/Kyiv).

### 6.2 AdsPower через bridge
- Дозволені команди (білий список): `list_profiles`, `create_profile`, `update_profile_group`, `open_profile`, `close_profile`, `find_profile`.
- Bridge викликає AdsPower Local API (`http://local.adspower.net:50325`, ключ API в локальному `.env` bridge).
- Результат `create_profile` автоматично пише `adspower_profile_id` в акаунт і подію `in_adspower`.
- Альтернатива для розробки: офіційний MCP `local-api-mcp-typescript` можна підключити в Antigravity для ручних тестів, але в продакшні bridge ходить у Local API напряму.

### 6.3 Telegram-бот
- Слухає клієнтські чати, де він доданий. Кожне повідомлення з запитом → LLM-парсер → JSON:
  `{intent: issue|replace|report|question, qty, geo, limit, account_codes[], urgency}`
- Невпевнений розбір (`confidence < 0.7`) → заявка з позначкою «перевірити вручну».
- Для `issue` система підбирає акаунти з `ready` (найстаріші за датою готовності) і створює пропозицію.
- Адмін отримує в особистий чат картку з кнопками **Апрув і видати / Змінити / Відхилити** (ті самі дії є в UI).
- Після апруву: акаунти → `issued`, клієнту в чат йде повідомлення з кодами кабінетів. Текст повідомлення — шаблон, який можна редагувати в налаштуваннях.
- Бот ніколи не видає нічого без апруву.

## 7. ШІ-агент

Агент працює лише через API системи, не має прямого доступу до БД, браузерів чи AdsPower.

| Інструмент | Рівень |
|---|---|
| `search_accounts`, `get_account`, `get_client_report`, `get_signals` | читання, без підтвердження |
| `parse_request`, `propose_accounts`, `draft_client_message` | готує чернетку |
| `change_stage`, `issue_accounts`, `send_client_message`, `bridge_command` | **тільки після апруву людини** |

- Усі дії агента пишуться в `account_events` з `actor = 'agent'`.
- Інтерфейс: чат в UI (розділ «ШІ-агент») і в особистому Telegram адміна.
- Кожен інструмент описаний окремим файлом-скілом `agent/skills/<name>.md` (опис, вхід, вихід, приклади).

## 8. Екрани UI

Еталон вигляду — тема Obsidian Pro (`docs/design/visual-concepts.html`, концепція 1).

1. **Дашборд**: KPI (спенд сьогодні, активні/всього, готові, заявки), воронка етапів + Off з розбивкою, таблиця акаунтів, заявки з Telegram, сигнали.
2. **Акаунти**: таблиця з фільтрами (етап, клієнт, постачальник, партія, сигнали), пошук по коду/ID/клієнту, масові дії.
3. **Картка акаунта**: KPI, графік спенду 7/30 днів, журнал подій, прив'язки, нотатка, пропозиції агента, кнопки переходу етапу.
4. **Канбан етапів**: колонки = етапи, drag-and-drop з валідацією статус-машини.
5. **Заявки**: список з фільтром за статусом, картка заявки з оригінальним текстом і розбором.
6. **Клієнти**: список і картка (видані акаунти, спенд, баланс, історія заявок).
7. **Постачальники і партії**: закупівлі, собівартість, відсоток відвалу по партіях.
8. **Фінанси**: спенд по клієнтах, нарахування за умовами, собівартість, маржа.
9. **Журнал подій**: глобальний, з фільтрами.
10. **Налаштування**: користувачі й ролі, шаблони повідомлень бота, токени інтеграцій, стан bridge.

Сигнали (генеруються фоновою задачею кожні 15 хв):
- проблемні оголошення > 0 у виданого кабінету;
- нульовий спенд сьогодні при спенді вчора > $10;
- перевірка 24 год закінчується;
- Clover не надсилав дані > 2 год;
- bridge офлайн > 15 хв.

## 9. Безпека

- Логін + обов'язковий TOTP 2FA, сесії з терміном дії.
- Ролі: `admin` (все), `operator` (етапи, без фінансів і видачі), `viewer` (читання).
- HTTPS через Caddy. Секрети лише в `.env`, не в репозиторії.
- Rate limit на `/api/clover/spend` і публічні ендпоінти.
- Щоденний бекап Postgres з ротацією 14 днів.

## 10. Етапи та критерії приймання

> **Порядок робіт (рішення власника, 30.09.2026):** спершу основний функціонал (MVP-1, ручні заявки, Clover, користувачі, фінанси, bridge, агент), Telegram — в останню чергу. Для Telegram обрано userbot на MTProto (api_id/api_hash) для читання чатів + окремий бот лише для карток адміна; заявки з Telegram створюватимуть ті самі записи `requests`, що й ручні.

**MVP-1: облік**
- Логін з 2FA, CRUD акаунтів, клієнтів, постачальників, партій.
- Статус-машина з валідацією, журнал подій, дашборд і картка акаунта як у референсі Obsidian.
- ✅ Приймання: акаунт проходить усі етапи від `purchased` до `issued`, кожен крок видно в журналі з автором; недозволений перехід повертає помилку.

**MVP-2: Telegram**
- Бот, LLM-парсинг, заявки, апрув з Telegram і з UI, повідомлення клієнту.
- ✅ Приймання: повідомлення «треба 2 кабінети PL ліміт 250» створює заявку з правильним розбором і двома запропонованими `ready`-акаунтами; після апруву вони в статусі `issued`, клієнт отримав повідомлення.

**MVP-3: Clover**
- Ендпоінт, збереження raw, парсер після отримання прикладу, зіставлення, графіки, сигнали.
- ✅ Приймання: спенд з Clover з'являється в картці акаунта не пізніше ніж через 5 хв після експорту.

**MVP-4: AdsPower bridge**
- Bridge, черга команд, статус у UI.
- ✅ Приймання: кнопка «Створити профіль» у картці акаунта створює профіль в AdsPower і записує його ID; при вимкненому макбуці команда чекає в черзі і виконується після підключення.

**MVP-5: ШІ-агент**
- Чат в UI і Telegram, інструменти з розділу 7, апрув для дій запису.
- ✅ Приймання: на «покажи всі кабінети Nord з проблемними оголошеннями» агент повертає правильний список; на «видай FB-0155 клієнту Vega» створює дію, яка виконується лише після кнопки апруву.

## 11. Правила роботи для Antigravity

1. Працювати по одному MVP-етапу за раз. Не переходити до наступного, поки не виконані критерії приймання поточного.
2. Перед кодом етапу — план у `docs/plan-mvp-N.md` (файли, міграції, ендпоінти) на підтвердження.
3. Структура репозиторію: `apps/web`, `apps/api`, `apps/bot`, `apps/bridge`, `agent/skills`, `docs`, `docker-compose.yml`.
4. Візуал брати з теми Obsidian (`docs/design/visual-concepts.html`): CSS-змінні з `[data-theme="obsidian"]` перенесені в `apps/web/src/styles/tokens.css` і підключені в Tailwind як токени; компоненти робити за розкладкою референсу.
5. Кожна зміна схеми БД — через міграцію Alembic.
6. Тести: pytest для статус-машини, парсера заявок і маппера Clover; мінімум один e2e-сценарій на етап.
7. Не додавати автоматизацію дій в інтерфейсі Facebook і не зберігати поля із забороненого списку (розділ 4).
8. Секрети та ключі не комітити; `.env.example` з усіма змінними без значень.

## 12. Відкриті питання

- Формат JSON від Clover Spend Export (потрібен приклад).
- Чи працює Clover з усіма кабінетами чи лише з активами ADS Clover Group.
- Умови оплати клієнтів для «Фінансів». **Реалізовано за замовчуванням: % від спенду (`clients.fee_percent`) + журнал оплат; баланс = початковий + оплати − нараховане.** Потребує підтвердження: чи потрібні фікс/передоплата-тариф/мінімалка, періоди нарахування (місяць), заморозка спенду на момент видачі, валюта.
- Скільки людей працюватиме в системі і з якими ролями.
